# File management, navigation and Markdown editor results

Implemented October 20, 2026, on top of the existing Office/Drive implementation. Existing planning material is preserved. Drive, S3 storage, file identities, sharing relationships, database tables and Office binary editing remain the foundation.

## Navigation and inventory

Create navigation is Docs, Sheets, Slides, Wiki, Drive, then All Files. Shared module configuration supplies titles, kinds, formats and Lucide icons (`FileText`, `Sheet`, `Presentation`, `BookOpen`, existing `Folder`, and `Files`). Each module has a distinct TanStack route: `/docs`, `/sheets`, `/slides`, `/wiki`, `/drive`, `/files`, under `/w/:workspaceId`.

The earlier Sheets/Slides problem came from using `/documents` with different query parameters. Distinct routes now drive active navigation, headings and breadcrumbs. Old `/documents?type=…` links redirect to the corresponding module. Old `/documents/:id` links resolve the authorized file kind and redirect to its canonical editor route. REST `/documents` endpoints stay compatible.

Docs, Sheets and Slides reuse `DrivePage` with constrained kinds and creation dialogs. Their upload pickers, drag/drop and API initialization validate the supported canonical formats: `.docx`, `.xlsx`, `.pptx`, respectively, up to 64 MiB. Browser ZIP/octet-stream MIME reports are normalized to the canonical MIME after extension validation. Existing signature checks and full Office package validation before attaching/opening remain in force. Legacy `.doc`, `.xls`, `.ppt`, macro formats and conversion imports are not newly supported.

Drive retains folders, general uploads and file management. All Files reuses the same browser, upload queue, dialogs, list/grid, selection, search, sorting, favorites, downloads, sharing, move/copy, trash and restore. It adds the mixed file-type filter and all four editor creation choices. Its root is a flat authorized inventory, including files inside folders. Folder navigation still scopes to that folder. Wiki retains its page tree and page-specific actions; a standalone Markdown upload remains a Drive preview rather than silently becoming a collaborative page.

My Files now combines owned and shared entries. Owner/Shared badges compare the actual file owner with the signed-in user; ownership filtering happens in the backend before pagination. The existing recursive Drive ACL still decides visibility and actions. Drive's hierarchical root includes shared entrypoints whose parent is inaccessible. Dedicated module inventories include accessible matching files throughout the hierarchy. A Shared badge does not imply management permission: workspace administrators and owning ancestors retain their existing explicitly granted management rights, while ordinary viewers/editors do not gain them. The old backend `view=shared` remains compatible, but there is no separate Shared With Me tab.

Central contracts live in `@lumolynk/contracts/files`, reexporting previous Office definitions for compatibility. Shared React module icons/routes live in the existing app package. No new runtime workspace package or database migration was needed for this follow-up.

## Markdown editor decision

Milkdown's rich-text/ProseMirror document model was appropriate for the initial Wiki fallback, but does not directly provide the requested raw Markdown source editor with persistent Edit/Preview/Split views. Converting a rich-text model to source and back on each mode switch would normalize source and disrupt collaborative selections. CodeMirror 6 was selected for its maintained Markdown language support, virtualized source editing, extensible commands and existing Yjs binding. Docs, Sheets and Slides continue to use ONLYOFFICE.

The editor uses CodeMirror 6, `y-codemirror.next` and the existing `y-websocket` transport. The same CodeMirror instance, Y.Text and local undo manager survive mode switches. The toolbar handles selections/cursor positions for bold, italic, strike, H1–H6, bullets, numbers, tasks, quotes, inline/fenced code, links, images, tables and horizontal rules. Undo/redo is scoped to local Yjs edits. Ctrl/Command B, I, Shift X and E format selections; standard undo/redo and Markdown continuation/indentation commands remain available.

Preview uses React Markdown with GFM, sanitation and trusted syntax highlighting. Raw embedded HTML is skipped; unsafe URL protocols are filtered. Links/images inserted through the toolbar also validate URLs. Tables scroll within the preview; images are bounded to the pane. Split mode stacks on narrow screens. CodeMirror virtualizes long source documents; the live preview is deferred to avoid blocking source updates. Rendering an extremely large preview still scales with document size, within the existing Wiki payload limits.

Transient session-renewal failures keep the mounted editor and local draft. Authorization rejection closes the editor as before. Unsent changes are held in memory while the page stays open; this does not add offline browser storage or guarantee survival after closing an offline page.

Primary library references: [CodeMirror system guide](https://codemirror.net/docs/guide/), [CodeMirror Markdown package](https://github.com/codemirror/lang-markdown), [Yjs CodeMirror binding](https://github.com/yjs/y-codemirror.next), [React Markdown security](https://github.com/remarkjs/react-markdown#security), [GFM support](https://github.com/remarkjs/remark-gfm), [rehype sanitation](https://github.com/rehypejs/rehype-sanitize).

## Existing Wiki data and rollout

New Yjs documents use `wiki.format = markdown-v1` and a `markdown` Y.Text. Markdown snapshots preserve source text directly, including GFM, code-fence languages and Unicode. The existing PostgreSQL update log, cross-instance notifications, persistence-before-broadcast, generation checks, access revocation, snapshots, versions and Drive/S3 cleanup are reused.

On opening an older Milkdown document, the backend reads its durable ProseMirror state, converts its supported CommonMark blocks/marks, and atomically stores the source model under the existing workspace lock. It increments the generation so old tickets cannot write into the new model. Historical version records and object keys are preserved; upgrading again is idempotent. A restored legacy revision is upgraded when subsequently opened. Legacy headings, code languages, list semantics, marks, safe images/links and Unicode have regression coverage. Unsafe legacy URLs and excessive nesting are rejected rather than silently imported.

Close existing Wiki editing sessions before rollout and deploy the API and shared web/desktop assets together. Wiki session requests now identify `markdown-v1`; old cached clients must reload/update. Generation checks prevent stale clients from overwriting upgraded state. No SQL backfill is necessary. Prior binary Office migrations and configuration documented in the original report still apply.
