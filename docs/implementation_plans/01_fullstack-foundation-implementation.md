### Implementation Order

**Phase 1: Database and Shared Packages**

Reference the architecture of https://github.com/zomeru/fidescript/tree/main/packages.

Implement or update:

- `packages/database`: Drizzle ORM, PostgreSQL schemas, migrations, and database client.
- `packages/auth`: Better Auth with secure session handling.
- `packages/contracts`: Shared Zod schemas, DTOs, API contracts, and inferred types.
- `packages/env`: Validated environment variables.
- `packages/typescript-config`: Shared TypeScript configurations.
- Additional shared packages only when they provide meaningful reuse.

For development, use **local PostgreSQL running inside WSL** rather than Neon.

**Phase 2: Backend API**

Create `apps/api` using Hono.

Implement a minimal but fully functional backend based on the requirements in documents 2 through 5.

Prioritize:

- Authentication and session management.
- User profiles.
- Workspace creation, switching, and membership.
- Workspace roles and permissions.
- Secure workspace-level data isolation.
- Core functionality needed to connect the frontend to real data.

Use modular, feature-based architecture, clear API contracts, centralized error handling, request validation, appropriate middleware, and automated tests.

Follow the documents for the actual business rules and implementation priorities. Do not attempt to implement every advanced feature in the first iteration.

**Phase 3: Frontend Implementation**

After the database and API foundation is working, implement and integrate the frontend in `apps/web`.

Use:

- React + Vite
- TanStack Router
- TanStack Query
- Existing styling and UI libraries

Reference the PNGs in `docs/sample_ai_generated_ui_flow_from_claude`.

Requirements:

- Build the relevant pages and flows represented in the screenshots.
- Preserve existing working components and styling where appropriate.
- Connect implemented features to the actual API and database.
- Replace relevant mock data and simulated actions with real functionality.
- Implement authentication, protected routes, and workspace switching.
- Ensure workspace-specific data is correctly scoped to the active workspace.
- Handle loading, empty, error, and unauthorized states.
- Make layouts responsive and accessible.
- Avoid decorative buttons or actions that appear functional but do nothing. Clearly disable features that are not implemented yet.

### Security and Scalability

Security is especially important because Lumo is a multi-tenant workspace platform.

Ensure:

- Users cannot access another workspace's private data without membership and proper authorization.
- Every workspace-scoped API operation validates membership and permissions on the server.
- Switching workspaces never exposes data from the previous workspace.
- Roles and permissions cannot be elevated through client-controlled inputs.
- Authentication uses secure, HTTP-only session cookies.
- API inputs are validated and sensitive data is never exposed unnecessarily.
- Database queries are parameterized, indexed appropriately, and designed for future growth.
- Cross-origin requests, CSRF protections, rate limiting, and error responses are handled securely.
- Workspace isolation and authorization are covered by automated tests.

Use DRY, KISS, and established TypeScript best practices. Avoid unnecessary abstractions, premature microservices, and overengineering.

### Verification and Completion

Do not stop after creating empty folders, placeholder routes, or database schemas.

Verify that:

1. PostgreSQL connects successfully from WSL.
2. Database migrations run successfully.
3. Users can register, sign in, sign out, and restore sessions.
4. An authenticated user can create and switch workspaces.
5. Membership and workspace authorization are enforced.
6. The implemented API endpoints perform real database operations.
7. The corresponding frontend flows work end-to-end.
8. Type checks, linting, unit tests, and relevant Playwright tests pass.

If some advanced features from the documentation are outside the initial implementation scope, clearly identify them as pending rather than pretending they work.

Implement in logical phases, validate each phase before continuing, and finish with a concise summary of implemented functionality, remaining work, and the commands needed to run Lumo locally.
